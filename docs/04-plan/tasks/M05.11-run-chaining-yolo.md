## Description

An external developer's preference: "do everything in one go, then verify" rather than step-by-step. This is not in tension with the step-by-step default — it is the same commands with the confirmation prompts suppressed and the questions batched. So it is a flag on the engine, not a new engine.

Three faces of one feature. Build them together:

| Form | Meaning |
|---|---|
| `/mae-run {a}..{b}` | Run delivery phases `a` through `b` in sequence. Phase names: `explore`, `req`, `design`, `plan`, `do`, `review`. |
| `/mae-req -> /mae-design -> /mae-plan` | Same thing, explicit command list. |
| `/mae-yolo [stop-phase]` | `/mae-run {current phase}..{stop-phase}`; default stop is `do`. |

Decision D32: `/mae-until` and cumulative commands (`/mae-spec`) are **not** built — chaining covers the need. Do not add them.

## Acceptance Criteria

- [ ] `/mae-run a..b` resolves the phase list, validates that `a` precedes `b`, and refuses ranges that skip a phase whose artifact is missing (e.g. `design..do` with no REQUIREMENTS.md → say what is missing, suggest the range that works)
- [ ] `->` syntax accepted as an equivalent explicit list; mixing with `..` is an error
- [ ] **One question round at the front:** before running anything, each phase's blocking questions are collected into a single numbered file; the user answers once. Non-blocking questions go into each artifact's `UNCLEAR:` flags, per the existing batched-round rule
- [ ] **One review at the end:** each phase's normal per-artifact review prompt is suppressed; a combined review lists every artifact produced, in order, and asks for approval once. Promotion to `docs/` happens only after that approval — the free-to-create / reviewed-to-mutate rule is unchanged
- [ ] `/mae-yolo` infers the current phase from what exists on disk (same state table as `/mae-help`, M04.15 — share it, do not duplicate it)
- [ ] `/mae-yolo` **never skips explore.** If `docs/01-explore/` is empty it runs explore first and stops for the question round — this is the one interruption it keeps, because building the wrong thing confidently is the worst outcome the framework can produce
- [ ] `/mae-yolo` and `/mae-run` ranges that include `do` commit after each task (task-ID message format from P42.01), regardless of the `[git] commit` setting, so an unattended run is recoverable at task granularity
- [ ] **Stop on first failure** inside `do`, same rule as multi-task execution in `/mae-do`
- [ ] Final report: phases run, artifacts produced (with links), questions answered vs. deferred, commits made, what was *not* done and why
- [ ] Documented in MAESTRO.md as a "documented, not advertised" feature: not in the quickstart, mentioned by `/mae-help all`, `/mae-yolo` carries a one-line warning
- [ ] Both commands added to `install.sh` download loop and to `.claude/commands/` wrappers

## Notes

**Why this moved out of M05.** It was filed as "orchestration over skills, needs M04.03" — but it orchestrates commands identically, and the v0.4.2 principle (build behavior before packaging) applies here too. The skill conversion converts it like everything else.

The question-batching is the actual value. The friction the developer described is not typing three commands; it is being interrupted three times.
