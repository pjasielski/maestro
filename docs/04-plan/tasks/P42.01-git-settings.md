## Description

The agent has no policy for when to commit, push, branch, or open PRs — so it either does nothing or does whatever seems reasonable in the moment. Give the user explicit control, with defaults that are safe for a stranger: commit often (local, revertible), never push (shared, not revertible).

Per-task rather than per-milestone because `/mae-do` already updates task status at that boundary, so the hook point exists, and a mid-milestone failure with milestone-level commits means untangling one large diff.

## Acceptance Criteria

- [ ] `[git]` block documented in MAESTRO.md § Session Visibility (or a new § Git Policy) with all five keys and their allowed values
- [ ] Defaults: `commit = "task"`, `push = "never"`, `branch = "milestone"`, `pr = "off"`, `merge = "never"`
- [ ] `/mae-do` commits after each completed task when `commit = "task"`, using the message convention below
- [ ] Commit message convention: `{type}({task-id}): {title}` with a `Task: {path}` trailer
- [ ] `branch = "milestone"` asks **once per milestone** before creating `milestone/m{NN}-{slug}`, not once per task
- [ ] Branch creation refuses when the working tree has unrelated dirty changes — offers to stash or to proceed on the current branch
- [ ] `pr = "milestone"` runs `gh pr create` at milestone completion, body assembled from task files + "Done when"
- [ ] The agent **always reports** git actions taken in its output ("committed 3 tasks, not pushed") regardless of settings
- [ ] Layered config: `maestro.local.toml` may only make git settings **more** conservative; a local setting that loosens project policy is rejected with a warning
- [ ] `install.sh` asks the commit-frequency question and writes the answer to `maestro.toml`

## Notes

The restrict-only rule for `maestro.local.toml` is the part that makes this safe in a team: a personal preference must never be able to weaken a shared git policy. It is also the general precedent for layered config — M04.07 should follow the same rule for every setting where project policy and personal preference can disagree.

Commit type (`feat`/`fix`/`docs`) is inferred from the task's own subject, not configured.
