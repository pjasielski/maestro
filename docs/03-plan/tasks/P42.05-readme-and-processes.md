## Description

Two gaps in what `/mae-do` leaves behind after building an app:

1. Generated READMEs have no reliable quickstart, or one inferred from config rather than verified. A quickstart that was right once and is wrong now is worse than none — people trust it and lose ten minutes.
2. Background processes (dev servers) survive the session, hold ports, and the user is never told they exist or how to stop them.

`/mae-do` already has a Verify step. If it ran the app to verify, it knows the working command — writing it down is nearly free.

## Acceptance Criteria

- [x] When a task creates or modifies a runnable project, `/mae-do` writes/updates `## Quickstart` in that project's README: install, run, verify
- [x] Quickstart commands are the ones **actually executed** during the Verify step, not inferred from config files
- [x] Staleness rule: when a task changes an entry point, port, required env var, or dependency, the quickstart is updated **in the same task**
- [x] Both `pip` and `uv` commands shown for Python projects (existing framework convention)
- [x] When the agent starts a long-running process, its report ends with the process, its port, its pid, and the stop command
- [x] `_summary.md` gains a `## Running Processes` section listing what this session started
- [x] `/sync` checks whether those processes are still alive and reports orphans
- [x] The agent states **intent**: whether it left something running deliberately ("left the dev server up so you can look at it") or cleaned up
- [x] Both conditions added to the definition-of-done (M04.13 task file; M04.13 itself is built later): a task is not done if the README lies or a process is silently orphaned

## Notes

The annoyance is not the running process — it is not knowing. Reporting intent costs one sentence and removes the whole problem.

Example output format:

```
⚙️  Running: dev server on :3000 (pid 48211, started by this session)
    Stop with: kill 48211   or   npm run stop
```
